# ADR-0001: Storage engine and data access library

- Status: proposed
- Date: 2026-09-19
- Slice: S-01 (decided before it starts; used from S-02 on)
- Related: A-04, A-15, INV-01, INV-04, INV-08, INV-09

## Context

State must survive restarts (A-15) and the model is relational: two state tables, an
append-only ledger with running balances, a message store. Reservations on one program must
be serialised by a database lock (A-04). Amounts are integer minor units that must never pass
through a float (INV-08). Every ledger row needs a CHECK constraint (INV-09). The service must
run locally from `docker compose up` with no managed service.

PostgreSQL satisfies all of this (row locks, BIGINT, NUMERIC, CHECK, JSONB for raw payloads)
and is the default choice for a NestJS service; MongoDB was considered in setup and dropped
because multi-row transactions and row locks are the core of this brief. The open choice is
the data access library, which decides how the repositories in `infrastructure/` are written,
how migrations run, and how `SELECT ... FOR UPDATE` is expressed.

## Options

### Option 1: Prisma
Pros: the most common choice in NestJS projects, generated fully typed client, first-class
migrations (`prisma migrate`), BIGINT maps to JS `bigint`, NUMERIC to `Decimal`. Cons: no
typed API for `FOR UPDATE`; the lock is a `$queryRaw` inside an interactive transaction, so
the most important query of the system is raw SQL; the query engine is a separate binary in
the Docker image.

### Option 2: Drizzle ORM
Pros: SQL-shaped typed builder, `.for('update')` is native, BIGINT with `mode: 'bigint'`,
migrations generated by `drizzle-kit` as plain SQL files, no runtime binary. Cons: younger
ecosystem, fewer NestJS examples, decimal columns come back as strings.

### Option 3: TypeORM
Pros: NestJS's documented default, `pessimistic_write` lock in the query builder. Cons:
weaker typing (bigint returns strings, `any` creeps in), decorators on entities pull the ORM
into the shape of the model, a long history of subtle bugs.

### Option 4: Kysely (query builder only) plus a migration runner
Pros: the tightest SQL control with full typing, `forUpdate()` native. Cons: no schema
management of its own, more code per repository.

## Recommendation

Option 1, Prisma, for reviewer familiarity and the migration story, with the row lock written
once as a raw statement inside `ProgramRepository.lockById` and covered by INV-01. If Marcin
prefers to avoid raw SQL on the critical path, Option 2 is the alternative with no other
change to the plan.

## Consequences

Whichever library is chosen, it appears only under `infrastructure/`; the lint boundary
forbids it in `domain/` and `application/`. Migrations live in the repo and run on container
start before the app listens. Money columns are BIGINT, rates NUMERIC, message payloads
JSONB.
